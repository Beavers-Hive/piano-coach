# piano-coach 壁打ちメモ

最終更新: 2026-10-15

## コンセプト

弾きたい曲の楽譜を渡すと、AI がその人のレベルと要望に合わせて指導計画を立てる。MIDI キーボードで弾いた演奏をその場で判定し、付きっきりで指導する。
目指すのは「ピアノを習いに行かなくてよくなる」こと。

## 要件（ユーザー案）

- 楽譜を PDF で渡す
- 曲を弾けるようになるまでの道筋を AI が考える
- レベルに合わせて指導する。初心者には「まず何をするか」を指示する
- MIDI キーボードを接続し、指示したフレーズの演奏を認識する
- 演奏を MIDI として記録し、AI が判定する。次のステップに進むか、練習内容を変えるかをその場で決める
- 強弱やテンポを含め、演奏として良いかまでアドバイスする
- 練習箇所を抜き出して表示する（例: このフレーズを右手だけ）。楽譜表示に加えて、ウォーターフォール（ノーツが落ちてくる）表示も出す
- 楽譜を読み込んだあとに目的（サビだけ弾きたい、など）をヒアリングし、指導計画を立てる
- 指くぐりなどの弾き方を 3D の手モデルで見せる
- 楽譜より簡単なアレンジでの指導もできる
- プラットフォームは PC。ネイティブか Web かは問わず、一番クオリティを出せるものにする
- エージェントは API 課金を避け、サブスクの Claude（`claude -p` など）で動かしたい

## 設計の基本方針（壁打ちで提案）

**LLM には「耳」と「目」をやらせない。決定的に処理できる部分はコードで行い、LLM は先生としての判断に専念させる。**

| 役割 | 担当 |
|---|---|
| 楽譜の読み取り（PDF → MusicXML） | OMR エンジン + 人による修正 UI |
| 抜粋・片手化・簡易アレンジの生成 | music21 などのコード（LLM は「どう変えるか」の指示だけを出す） |
| 演奏の採点（音の正誤、タイミングのずれ、強弱のカーブ） | スコアアライメント（DTW など）でコードが数値化する |
| 1 回の演奏直後の即時フィードバック | コード（ミスした音を赤く表示する等） |
| 指導計画、次の課題の選択、言葉でのアドバイス | Claude |

## 技術的な論点

### 1. PDF → 楽譜データ（最大のリスク）
- OMR（光学楽譜認識）の精度は、まだ完璧ではない。候補は Audiveris（OSS）、oemer、商用 API など
- MVP では MusicXML / MIDI の入力に絞る（MuseScore などから入手する前提）。PDF 対応は後のフェーズに回す
- PDF 対応時は、読み取り結果を人が直せる UI がほぼ必須になる

### 2. 表示
- 楽譜の描画: OpenSheetMusicDisplay か Verovio
- ウォーターフォール: Canvas / WebGL で自前実装する
- 3D の手: Three.js とリグ付きの手モデル。運指は推定（pianoplayer 等）またはキーフレームで付ける。コストが最も高いので後のフェーズに回す

### 3. MIDI 入力
- Web MIDI API（Chrome / Edge / Electron）で十分に扱える
- サスティンペダル（CC64）も取れる
- velocity の出方は鍵盤ごとに違うので、キャリブレーションが必要

### 4. エージェント実行基盤（サブスクで動かす）
- Claude Agent SDK（TypeScript）を使い、ローカルにログイン済みの Claude Code を裏で動かす
- コンテキストは会話履歴に頼らず、状態をすべて DB やファイルに置く。具体的には学習者プロファイル、指導計画、進捗ログ、採点結果
- アプリ側が MCP サーバーとしてツールを公開し、Claude はツール経由で状態を読み書きする
  - 例: `get_learner_profile` / `get_score_outline` / `create_exercise(measures, hand, tempo, simplify)` / `get_attempt_result` / `update_plan`
- セッションは resume で継続する。履歴が壊れても状態は DB に残っているので、いつでも作り直せる
- 長時間起動したプロセスに stream-json で入力を流し、`claude -p` を毎回起動するコストを避ける
- 1 打鍵ごとに LLM を呼ぶとレート制限に当たる。LLM を呼ぶのは「数回の試行ごと」と「区切りのタイミング」に絞る
- 注意: 自分で使う分にはサブスクで回せる。他人に提供する段階では API キー課金が前提になる（規約は要確認）

### 5. プラットフォーム
- Claude Code をローカルで動かす以上、ローカルアプリになる
- 案: React + Vite のフロントエンド、Node のバックエンド（Agent SDK と MCP）、Python ワーカー（music21 と OMR）
- 最初はローカル Web アプリとして作り、後で Electron に包む

## フェーズ案

- **MVP**: MusicXML 入力 → ヒアリング → 指導計画 → 抜粋の楽譜とウォーターフォール表示 → MIDI 演奏 → 自動採点 → Claude の講評と次の課題
- **P1**: PDF 入力（OMR と修正 UI）
- **P2**: 簡易アレンジ、運指の推定と表示
- **P3**: 3D の手モデル
- **P4（任意）**: Web カメラによる手のトラッキング（MediaPipe）で、指使いや手の形をチェックする

## 決定事項（2026-10-15）

- 自分用。サブスクの Claude で動かす
- 手元の鍵盤は Roland JUNO-DS88（88 鍵）。ただし 25 / 49 / 61 鍵などにも汎用的に対応させる
- エージェントは当面 Claude。将来 Gemini に差し替えられる設計にする
- **ハッカソン向け**。実用性より「すげぇ、こんなことできるんだ」と思わせることを優先する
- 3D 表示はクオリティ最優先で、MVP に入れる
- 体験は「楽譜を渡すだけ」の楽さを重視する
- MCP 方式はやめる。Agent Native App 方式にする（Python のハーネスが、claude-agent-sdk 経由でローカルの Claude Code を動かす）。レッスンの途中でプロバイダを切り替えることは想定しない
